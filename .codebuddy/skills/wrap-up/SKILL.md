# 需求收尾（评审 → 测试 → 提交）

三步走，每步通过才进下一步；任何一步失败，修复后从头重跑该步。

## 前置：确认收尾范围

`git status --short` + `git log --oneline -5` 确定要收尾的改动集：
- 工作区未提交改动 + 可能已有若干本地未 push 提交；
- 与用户确认范围（默认：本次需求产生的全部改动）。发现不认识的文件/暂存条目先问，不盲目纳入。

## 第 1 步：代码评审并修复

对改动集做 `git diff`（未提交）/ `git log -p`（本地提交）逐文件评审，检查项按优先级：

1. **项目硬约束**（AGENTS.md）：分析逻辑必须基于 google/pprof 库不自研；路径白名单不弱化；60s CPU 上限可配置（`MaxCPUSeconds`）；配置顺序 flag > 环境变量 > 默认值；暴露面变化需在提交说明中声明。
2. **正确性**：边界条件（nil/空切片/越界切片表达式）、错误处理不吞错、并发安全、资源泄漏（body/文件 Close）。
3. **一致性**：新代码与既有模式一致（复用 core 已有聚合/解析函数，不重写）；命名无 dash；表驱动测试。
4. **过度设计**：无单实现接口、无投机配置项、无未被使用的导出符号——删。

发现问题的处置：
- 直接修复（评审+修复一体，不列清单等确认，除非修复会改变对外行为/协议）；
- 修不完或有争议的，列为遗留项写进最终汇报，不阻塞收尾。

## 第 2 步：跑通全部验证

依次执行，任何一步失败先修复再重跑（禁止跳过或缩小范围）：

```bash
go build ./...
go vet ./...
go test -count=1 ./...
```

环境注意（本机 go1.22 < go.mod 要求的 1.26）：
- 优先用 `GOTOOLCHAIN=auto go ...`（自动下载工具链，需 GOPROXY 镜像）；或找本机已装的高版本 go（如 `/tmp/go126/bin/go`，勿依赖其长期存在）；
- 旧 go 报 `GOROOT` 污染时用 `env -u GOROOT` 或 `GOROOT=` 覆盖；
- 测试失败先判定是本次改动引入还是既有失败：`git stash` 后在干净树上复跑对比，既有失败记录并知会用户，不擅自"顺手修"无关测试。

全部通过后输出一行验证结论（命令 + 结果）。

## 第 3 步：整理提交

1. **分组**：按逻辑单元拆分提交（一个功能/一个修复一个 commit），不相关的改动不混入；`git add <明确路径>` 逐个暂存，**add 前后各跑一次 `git status --short` 核对暂存区与预期完全一致**，多余的 `git restore --staged` 剔除。
2. **不入库的确认**：`.mcp.json`、`/tmp` 产物、本地脚本等本地配置默认不提交（核对 .gitignore 是否覆盖）。
3. **提交信息**：中文一句话说清"改了什么+为什么"，涉及行为变化的写明影响面。不使用 `git commit --amend` 除非用户明确要求。
4. **汇报**：列出每个 commit 的 hash + 信息 + 文件数；**push 必须等用户明确指示**，默认只做本地提交。
5. 收尾输出：评审修复项摘要（含遗留项）、验证结果、commit 列表、待用户决策事项（push/tag 等）。
